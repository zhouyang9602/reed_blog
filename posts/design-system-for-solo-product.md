做独立产品的人，常常会在某个深夜遇到同一个问题：这个新页面应该长什么样？

按钮要不要圆角？标题用 32px 还是 36px？空状态应该居中还是靠左？这些问题都不难，但每一次重新决定，都会从真正重要的工作里偷走一点点注意力。

设计系统不是大公司的专属仪式。对一个人或两三个人的小团队来说，它更像一份写给未来自己的说明书。

## 先定义“为什么”，再定义组件

很多设计系统从颜色和按钮开始，最后变成一页无人维护的组件清单。真正有用的起点应该是一个句子：

> 我们希望用户在使用产品时，感到清晰、可信，并且总能知道下一步该做什么。

这句话决定了很多细节。如果目标是“清晰”，那么信息层级就比装饰性插画重要；如果目标是“可信”，那么稳定的间距和一致的反馈可能比一时的视觉惊喜更关键。

我在做个人项目时，会先把设计原则压缩成三条：

1. **内容优先**：界面退后一步，让文字和任务成为主角。
2. **安静但明确**：少用抢眼的颜色，但关键操作必须足够明显。
3. **允许节奏变化**：标题、正文和辅助信息之间要有可感知的层次。

原则不是口号。它们应该能在两个方案难以取舍时，帮你做出更快、更稳定的判断。

## 从最小的一组决定开始

一个小产品不需要一百个组件。下面这些基础决定，已经能覆盖大多数页面：

| 层次 | 需要先固定的内容 |
| --- | --- |
| 颜色 | 背景、正文、次要文字、品牌色、危险色 |
| 字体 | 标题、正文、等宽字体与三档字号 |
| 空间 | 4px 或 8px 的间距基数 |
| 形状 | 卡片和控件的圆角、边框、阴影 |
| 反馈 | hover、focus、loading、empty、error |

先写进 CSS 变量，再开始做页面。这样你修改品牌色时，不需要在十几个文件里搜索十六进制色值。

```css
:root {
  --color-bg: #f5f7fb;
  --color-surface: #ffffff;
  --color-text: #172942;
  --color-muted: #6b7c91;
  --color-brand: #2468e8;
  --radius-card: 16px;
  --space-unit: 4px;
}
```

变量不是为了让代码看起来更“工程化”，而是为了让改变发生得更便宜。你越早接受方案会变化，越应该减少重复决定。

## 组件需要上下文，而不是无穷选项

我不喜欢给按钮加十几个布尔参数。一个人维护组件时，真正有价值的不是“什么都能配”，而是“下一步通常是什么”。

例如，一个按钮通常只有三类：

- 主操作：提交、购买、开始；
- 次操作：取消、返回、稍后再说；
- 文本操作：查看详情、展开更多。

每多一种按钮，就多一次选择。每多一次选择，就多一个让界面变得不一致的机会。

与其维护庞大的配置项，不如直接写出可以在真实页面里复用的 HTML。组件库可以小，但使用方式要稳定。

## 让设计系统活在页面里

设计系统最怕两件事：没人看，以及看了以后和真实产品不一样。

我的做法是保留一个简单的 `styleguide.html`，里面不是抽象说明，而是当前产品正在使用的标题、按钮、输入框、文章卡片和空状态。每次改了样式，就顺手打开这个页面检查一遍。

还有一个小习惯：新建页面前，先找现成页面里有没有可以复用的结构。大部分“新设计”，其实只是已有模式的重新组合。

## 留给变化一点位置

设计系统提供一致性，但不应该消灭表达。博客的首页可以有一点戏剧性，活动页可以更热烈，个人介绍可以更自由。稳定的部分是控件、文字层级和交互反馈；可以变化的是叙事与情绪。

对一个独立产品来说，最好的设计系统通常不是最完整的，而是你愿意持续使用的那个。它让重复的问题有答案，把宝贵的时间留给真正需要创造力的部分。

这大概就是设计系统最朴素的收益：**少想一点按钮，多想一点产品。**
