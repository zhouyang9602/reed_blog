我第一次把 AI 放进开发流程时，期待它替我写完所有代码。用了几个月后，真正留下来的却不是“自动生成”，而是几个更细小的改变。

它像一个随时在线的讨论对象：不会因为问题太基础而皱眉，也不会因为你换了第三种思路而不耐烦。关键在于，你要把它放在工作流的正确位置。

## 位置一：把模糊的问题说清楚

很多开发任务卡住，不是不会写代码，而是问题还没有被描述清楚。

比如“帮我优化这个页面”，几乎无法得到有价值的答案。换成下面这样，事情就不一样了：

> 这是一个文章列表页。手机端首次加载时图片区域会跳动，用户下滑到第二屏后展开筛选器会出现明显卡顿。代码使用原生 JavaScript，数据量约为 200 条。请先列出最可能的性能原因，再给出按收益排序的排查步骤。

我没有要求它立刻写代码，只是要求它帮我整理假设。这个过程本身就会暴露信息缺口：图片是否有固定尺寸？筛选器展开时是否触发了整页重排？数据是否一次性渲染？

AI 在这里的价值，不是答案，而是更好的问题。

## 位置二：生成可以丢弃的草稿

写一个不熟悉领域的函数时，我会先让 AI 给出两三种实现，再把它们都当作草稿。

草稿的意义是可以被扔掉。它让我快速看到边界条件、API 的不同用法和潜在的反例。最终代码仍然由我逐行阅读、修改并测试。

我常用的一条规则是：

- 让 AI 处理“可能性”；
- 让自己负责“确定性”。

生成候选方案属于前者，判断它是否适合当前系统属于后者。两者混在一起，麻烦就开始了。

## 位置三：做第二双眼睛

代码评审时，我会把一小段逻辑和它的目标一起交给 AI，让它专门寻找：

1. 未覆盖的边界条件；
2. 命名与注释之间的不一致；
3. 可以被删除的抽象；
4. 不明显但危险的状态变化。

它偶尔会提出看似正确、实际错误的建议。但即使错误也有用：为什么这个建议不成立？是它缺少了哪部分上下文？这些追问会让我对代码的理解更具体。

## 位置四：把重复劳动变成脚本

有些工作每周都要做：整理发布记录、批量重命名图片、从 Markdown 生成目录。它们不复杂，却会持续占用注意力。

这类任务适合先让 AI 给出一个小脚本，再由我补充错误处理和安全边界。

```js
function estimateReadingTime(content) {
  const chinese = (content.match(/[\u3400-\u9fff]/g) || []).length;
  const latin = (content.match(/[A-Za-z0-9_]+/g) || []).length;
  return Math.max(1, Math.ceil(chinese / 400 + latin / 220));
}

console.log(estimateReadingTime("一段中文和 some English words."));
```

脚本最终能不能用，不取决于它写得多漂亮，而取决于你是否理解它会碰到哪些输入。

## 不应该交出去的部分

有几件事，我会刻意保留给自己：

- 最终的产品判断；
- 关键数据的解释；
- 涉及隐私和权限的决策；
- 自己读不懂却准备合并的代码。

最后一条尤其重要。AI 可以缩短从零到可运行的距离，却无法替你承担系统上线后的理解责任。

## 工作流真正的变化

AI 没有让我少工作。它改变的是工作的分布：少了在空白文件前犹豫的时间，多了验证、阅读和做判断的时间。

如果把软件开发生命周期画成一条线，AI 在“起草”和“检查”两端最有价值，在“理解目标”和“承担责任”两端最需要人类。

我现在的日常节奏大概是：

1. 先自己写清楚问题与验收标准；
2. 用 AI 扩展方案空间；
3. 选择一条足够简单的路线；
4. 自己写核心逻辑；
5. 让 AI 帮助寻找遗漏；
6. 用测试和真实使用确认结果。

工具会继续变化，但这条顺序大概不会。**先把问题想清楚，再让工具加速。**
